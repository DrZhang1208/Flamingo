# 冷启动封面与播放进度恢复

## 原因

启动流程先连接 MediaController，再从 Room 读取整份播放列表，最后读取当前歌曲和进度。界面因此先用空歌曲/零进度绘制。封面首次解析成功还会经过 300ms 的切歌淡入，延长了占位图可见时间。

## 修改

- Room 保存播放状态成功后，更新 MMKV 中只含当前一首歌曲的启动预览快照。快照失败不影响 Room 保存；状态写入串行处理，避免数据库与快照交错。清空当前歌曲时移除快照，损坏快照安全忽略。
- Application 在 Activity 首次组合前读取单曲预览，立即发布歌曲、背景 URI 和保存进度，并提前向共用 Coil loader 请求封面，不解析完整队列、不阻塞主线程等待 Room。
- 权威 Room 状态独立于媒体服务绑定异步读取，先于大队列恢复。初次升级没有预览时也走这条路径；之后通过正常保存自动建立预览。
- 队列尚未恢复期间，播放页的初始进度条、时长和文本从预览初始化。真实播放器有当前曲目后立即以其进度为准，合法的 0 进度不回退旧保存值；未知播放器时长暂用歌曲元数据。
- 尚无真实曲目或 UI/播放器曲目不一致时跳过播放状态回写，防止启动恢复完成前退出，把预览进度覆盖为 0；时长未知时也保留显示进度。
- 恢复完整队列前，在主线程、prepare 互斥锁内检查播放器是否已有曲目；用户已经开始播放新歌时跳过旧队列恢复，不再把旧列表投递覆盖回来。保存歌曲不在队列时恢复单曲，避免错选队列首项。
- 首个有效封面直接显示，后续真实切歌继续保留可打断的 300ms 淡入。预加载与播放界面复用同一请求构造方式，不重复预加载同一封面 URI。

封面仍需要真实文件解码或网络读取；本修改提前启动读取并去除服务/整队列/首图淡入的串行等待，不用同步解码阻塞主线程。

## 验证

- 新增纯逻辑回归覆盖控制器未连接时的保存进度、真实跳到 0、播放器时长未知、负值及越界进度，共 4 项；全套 132 项单元测试通过。
- 新增 Android 回归覆盖单曲快照的封面/进度序列化、清空与损坏数据，使用独立 MMKV 测试实例；封面回归在首图载入后的前两个动画帧检查已完整显示，同时保留快速切歌淡入/打断检查。
- Android 测试 APK 编译通过；未运行设备测试，本地结果不能证明目标手机的冷启动耗时。

最终构建：Release 与关键 Lint 通过；安装包已复制到下载目录，WebDAV 上传完成，远端临时文件回读 SHA-256 与本地一致后 MOVE 发布成功。上传中一次分块连接错误通过自动重试恢复。
